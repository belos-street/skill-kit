# rag-graphrag：GraphRAG

## 通用原则（不限语言/框架）

GraphRAG 是 RAG 的图谱化演进：把文档**实体化、关系化**后再回答，解决"答案分散在多处、需要跨文档推理"的问题。

- **核心流程**：①LLM 抽取文档中的实体（产品/命令/概念/版本）与关系（依赖/调用/报错关联）→ 构建知识图谱；②社区检测（如 Leiden）把图谱分成语义社区，LLM 为每个社区生成摘要；③查询时既做向量检索，也按实体匹配沿图谱多跳聚合证据；
- **擅长的问题**（论文经验教训明确点名）：
  - **多角度总结**——"常见问题有哪些"这类需要聚合多个分散主题的问题，图社区摘要比"检索 top-k 拼接"更完整；
  - **跨文档关联**——错误信息散落在不同手册/工单里，图谱能沿"报错 → 组件 → 排查步骤"链路聚合；
  - **全局性问题**——"整个平台有哪些已知风险"这类无单点答案的问题；
- **代价（务必评估）**：建图成本高（每文档 1~N 次 LLM 抽取调用，文档量大时昂贵且慢）；图谱需随文档更新重建；延迟高于普通 RAG；
- **选型判断**：**文档量大、问题跨文档/全局性强 → 值得**；文档量小、问题单点定位即可 → **普通 RAG 足够，GraphRAG 是纯浪费**。先做意图分布统计（多角度总结类占比高吗？）再决定（论文实测多角度总结类占比约 14.7%）。

## 落地建议（按需启用）

- **默认不引入**：chunk 级 RAG（标题感知分块 + 双通道检索）覆盖单点定位型查询；
- **触发条件**：①接入多系统文档后跨文档问题占比上升；②评估显示多角度总结类准确率持续偏低（见 `rag-evaluation.md` 意图分项指标）；
- ⚠️ 未启用前**勿在 schema/管线里预留图谱表**——等真实需求（YAGNI）；
- **试点验证**：取 20~30 条多角度总结类黄金集，对比 chunk RAG vs GraphRAG 的 coverage 胜出率（沿用 rag-evaluation 的 win-tie-loss 方法，论文 78% coverage 胜出率是强基线），并记录建图耗时/成本做性价比对比。
