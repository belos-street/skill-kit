# rag-multi-turn：多轮对话 RAG

## 通用原则（不限语言/框架）

对话式 RAG 的核心问题：**用户的第 N 轮问题往往依赖前文**（"那它呢？"、"这个报错怎么处理？"、"再详细点"），直接拿去检索必然失败。

- **追问改写（query rewriting with history）**：每轮检索前，把「历史对话 + 当前问题」交给 LLM，重写为**独立、自包含**的问题（如"它" → 上一轮提到的具体对象），再走单轮 RAG 链路——这是最通用、改动最小的方案，**与 rag-query 的意图分类/改写天然衔接**（多轮改写产出 → 意图分类 → 单轮改写 → 检索）；
- **历史压缩（context compression）**：对话很长时，定期用 LLM 把历史摘要成"本轮检索所需的背景"，防止上下文爆掉、也防无关历史干扰检索；
- **上下文管理**：维护"历史窗口"（如最近 N 轮）+ 显式状态（当前话题/上次引用的文档），比盲目堆全部历史更稳；
- **与单轮的取舍**：多轮带来延迟与成本（每轮多 1~2 次 LLM 调用），且引入状态管理复杂度。**能单轮解决的问题别为对话而对话**——先评估多轮追问在真实查询中的占比（见 rag-evaluation 的意图分布统计）再决定。

## 落地建议（按需启用）

- **默认单轮**：产品形态/需求为单轮问答时，保持无状态、可水平扩展，不做多轮；
- **启用方式**（若产品要求多轮）：在单轮问答链路外增加会话层——入口层维护 `sessionId → history[]`，每轮先调"历史改写"再进入现有 `answer()` 链路，**改动集中在入口层，核心 Service 层无需大改**；
- ⚠️ 未启用前**勿在问答链路里预留多轮参数**（如可选的 history 入参）——YAGNI，等需求落地再改。

## 验证方式（通用）

- 启用后测试集：构造 3~5 轮追问链（每轮含指代/省略），断言"改写后的问题"能独立检索到正确文档；
- 回归：确认加多轮后单轮问题准确率不降（历史改写误伤单轮是常见坑）。
