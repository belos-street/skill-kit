# doc/ 分层详解

> `doc/` 是项目文档的**唯一存放处**，供真人与 AI 共读。**不要**把项目文档放进 `.agents/`。

## 一、七层结构与职责

| 目录 | 定位 | 权威性 | 命名 |
| --- | --- | --- | --- |
| `doc/api/<version>/` | **接口与需求事实层**：接口定义、字段、枚举取值、业务规则、前后端联调说明 | 长期权威，按版本归档 | 版本目录 `v1.19.0/`；文件按主题命名 |
| `doc/business/<域>.md` | **业务域知识**：组件地图、枚举速查、API 落点、数据流、关键检查清单、已知坑、不适用场景 | 随业务演进持续补充 | 一域一篇，kebab-case，与源码域目录对齐 |
| `doc/architecture/` | **技术架构与开发指南**：目录约定、模块开发指南、路由/导航、公共组件、测试、环境构建、样式体系、权限 | 稳定 | 主题命名 |
| `doc/design/` | **设计思路文档**：新版本设计稿的推导过程与决策 | 按版本归档 | `v<版本>/<模块>-design.md` |
| `doc/plan/` | **改造与升级计划**：分优先级（P0/P1/P2）的清单 + 状态跟踪 + **明确不做清单** | 计划层 | 主题命名 |
| `doc/templates/` | **产出骨架模板**：变更三层文档、代码骨架、设计文档模板 | 模板 | 按用途分子目录 |
| `doc/changes/<change-id>/` | **当次变更层**：proposal / design / tasks 三层文档，随代码提交可追溯 | 单次有效，验收后归档不删 | `YYYYMMDD-<kebab主题>` |

## 二、三条关键边界

1. **`doc/api`（事实层）vs `doc/changes`（变更层）**：
   - `doc/api` = 长期权威，按版本归档；
   - `doc/changes` = 单次需求，按 change 归档；
   - **接口变更时：先在 `doc/api` 更新事实，再在 `doc/changes` 记录本次影响面。**
2. **`doc/business`（业务事实）vs `.agents/rules`（行为约束）**：业务域知识随代码演进、真人也要读 → 放 `doc/`；行为约束面向 AI → 放 rules。
3. **`doc/plan`（要做什么）vs `doc/changes`（做了什么）**：计划层用状态标记（⬜ 待办 / 🔧 进行中 / ✅ 完成 / ❌ 放弃），完成即勾选并注明提交；变更层逐次归档。

## 三、各层模板要点

### doc/business/<域>.md（最高频、最值得沉淀）

固定六段式，**「已知坑」是价值最高的部分**：

```markdown
# 业务域：<域>（<中文名>）
## 适用场景（关键词）        # 便于 AI 判断该不该读这篇
## 组件地图（真实路径）      # 页面/组件 → 源码路径，避免重新摸代码
## 枚举速查（来源文件）      # 枚举值 → 含义，标注取值来源
## 数据流                    # 关键数据的流转链路
## 关键检查清单              # 改动本域时必须自查的点
## 已知坑                    # 事故与陷阱，复盘三问的落点
## 不适用场景                # 明确边界，避免误用
```

配套 `doc/business/README.md` 写目录约定 + 现状清单（哪些域已就位）。

### doc/architecture/module-guide.md

新建模块的**唯一操作手册**：目录结构 → 列表页（筛选配置 / 表格列配置 / 主组件结构）→ 表单页（状态管理 / 主组件结构）→ API 层模式 → 路由配置 → i18n 命名 → **新建模块检查清单** → 所需信息清单。

> 配套 `doc/templates/code/` 放可复制的代码骨架（列表页 / API / 状态管理 / 下拉 hook / i18n）。**指南讲为什么，模板给可复制的骨架**，两者分工。

### doc/templates/change/（三层变更文档）

| 文档 | 回答 | 必须含 |
| --- | --- | --- |
| `proposal.md` | 为什么做 | 背景与问题 / 目标与非目标 / 方案选型 / **影响面清单** / 验收标准 |
| `design.md` | 怎么做 | 技术设计 / 涉及文件清单（改动·新增·删除）/ 与接口文档的对应 / 风险与已知坑 |
| `tasks.md` | 拆着做 | 任务列表，每项 = 目标 → 涉及文件 → 验收点，按依赖排序 |

### doc/plan/

每项计划独立成文、带状态跟踪；**必须有「明确不做」表**（项 + 原因），避免同一话题反复讨论。

## 四、索引与维护

1. **入口索引**：`AGENTS.md` 第十节按层列出 `doc/` 全部入口，每项都要有「何时阅读」列；
2. **目录自索引**：`doc/business/README.md`、`doc/changes/README.md`、`doc/plan/README.md` 各自维护目录约定与现状；
3. **同步义务**：新增/移动文档 → 同步 `AGENTS.md` 索引；路径变更 → 同步所有交叉引用（rules、workflows、architecture 文档内部链接）；
4. **归档不删**：`doc/changes/` 验收通过后保留归档，保证「为什么当时这么改」可追溯；
5. **接口变更双写**：先 `doc/api` 更新事实，再 `doc/changes` 记影响面。

## 五、按需加载策略

`doc/` 体量会持续增长，**不靠常驻加载**，而靠「入口索引 + 规则指引」实现按需读取：

- `AGENTS.md` 提供「想了解 X → 读哪」的映射表；
- rules 里写明「涉及本域前先读 `doc/business/<域>.md`」；
- workflows 的步骤里明确「读项目事实」是第几步。

> 这是把「上下文预算」当资源管理：入口只放指针，长内容等真正需要时再读。
