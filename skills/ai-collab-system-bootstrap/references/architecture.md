# 体系架构详解

> 本文件解释「为什么这样分层」，以及体系在真实项目中演进出的经验教训。搭建时只需读 SKILL.md 的流程；**设计或改造体系本身**时读本文件。

## 一、七层模型

```text
项目根
├── AGENTS.md                    # L0 入口（人工维护，跨工具通用）
├── .agents/                     # AI 协作体系（面向 AI）
│   ├── rules/                   # L1 行为约束与闸门（alwaysApply）
│   ├── workflows/               # L2 按意图路由的流程
│   ├── skills/                  # L3 跨项目可复用能力
│   └── memory/decisions.md      # L4 追加式决策日志
├── doc/                         # L5 项目文档（人机共读）
└── .husky/ + eslint/            # L6 机器校验
```

### 分层依据

| 层 | 面向谁 | 变化频率 | 加载方式 |
| --- | --- | --- | --- |
| rules | AI | 低（约定稳定） | `alwaysApply: true` 常驻 / `false` 按需 |
| workflows | AI | 低 | 被 `workflow-guide` 决策表路由后读取 |
| skills | AI（可跨项目） | 低 | 按 description 触发 |
| memory | 人 + AI | 高（持续追加） | 任务开始前主动读 |
| doc/ | 人为主、AI 共读 | 高 | 按 AGENTS.md 索引 + rules 指引按需读 |

**关键判断**：`.agents/` 面向 AI 的**可执行约束**，`doc/` 面向人的**项目事实**。同一个知识点不要两边都写——写在不属于它的层，会导致双份维护与事实分叉。

## 二、放置原则（决策树）

```text
这份内容要给谁用？
├── 只有 AI 需要遵守的行为约束 → .agents/rules/
│   ├── 本项目专属（设计体系、API 约定、i18n） → rules
│   └── 跨项目通用方法论 / 工具能力 → .agents/skills/
├── AI 按场景执行的步骤流程 → .agents/workflows/
├── 一次敲定、长期遵守的结论 → .agents/memory/decisions.md
└── 人与 AI 都要读的项目事实 → doc/
    ├── 接口 / 需求事实（按版本权威） → doc/api/
    ├── 业务域知识（组件地图/枚举/落点/已知坑） → doc/business/
    ├── 技术架构与开发指南 → doc/architecture/
    ├── 设计思路文档 → doc/design/
    ├── 改造与升级计划 → doc/plan/
    ├── 产出骨架模板 → doc/templates/
    └── 当次变更记录 → doc/changes/
```

### 三个易错点

1. **项目专属 vs 跨项目通用**：设计 token 对照表、spec-first 闸门属于**项目专属**→ rules；「如何做需求探索」「UI/UX 方法论」「Playwright 用法」属于**通用能力**→ skills。判据是：这份东西原封不动复制到另一个项目还成立吗？
2. **事实 vs 约束**：`doc/business/rule.md` 记「语言下拉数据源是后端接口」是**事实**；`.agents/rules/i18n.md` 写「新增文案必须中英镜像」是**约束**。事实随代码演进，约束随团队约定。
3. **入口 vs 内容**：`AGENTS.md` 只做索引。任何「因为放这里方便」而堆进入口的长内容，都会让入口逐渐失效（没人读完 → 没人维护 → 与事实脱节）。

## 三、体系演进教训（原型项目决策精华）

以下是从原型项目 15 条决策（D1–D15）中提炼的**可迁移结论**：

| # | 结论 | 可迁移性 |
| --- | --- | --- |
| 1 | AI 配置目录用 `.agents/`（业界约定、跨工具通用），不用工具私有目录 | ✅ 通用 |
| 2 | 入口文档用 `AGENTS.md`（跨工具约定）且**人工维护**，索引手动同步 | ✅ 通用 |
| 3 | 项目文档统一 `doc/`，**不移入** `.agents/` | ✅ 通用 |
| 4 | 新增 skill 采用**手动复制 + 手动更新索引**，不引入自动化 skill 管理工具（数量有限时更可控） | ✅ 通用 |
| 5 | 需求/设计探索类能力**收敛到单一来源**（一个合集 skill），删除重复的自建 skill，避免链接失效与重复维护 | ✅ 通用 |
| 6 | 复杂需求启用「规范先行闸门」（三层文档 + 停下等确认） | ✅ 通用 |
| 7 | `doc/` 分「接口事实层 / 业务域层 / 架构指南层 / 模板层 / 变更层」；业务域知识不进 skills | ✅ 通用 |
| 8 | **软约束必须硬化**：可机械判定的部分下沉为 hook / lint 规则 | ✅ 通用 |
| 9 | skills 与 rules 的边界 = 「可跨项目复用」vs「本项目专属」 | ✅ 通用 |
| 10 | 目录结构重构时**行为与 URL 不变** + `git mv` 保历史 + 每单元独立提交验证 | 场景性 |
| 11 | 数据源类改造（如枚举/下拉）必须先列**影响面清单**，否则必漏改 | 场景性 |
| 12 | 已敲定的事实**不改名**（如历史拼写错误），避免无收益的扩散改动 | 场景性 |
| 13 | 工作流步骤中嵌入「复盘三问」，把事故落回文档，让体系自生长 | ✅ 通用 |
| 14 | 工具链选型要区分「存量迁移成本」与「新工程零包袱」——两者结论可以不同 | 场景性 |
| 15 | 决策记录**只追加不覆盖**，编号递增；「过期检查」是伪命题（追加式事实无机器可判定的过期态） | ✅ 通用 |

### 最重要的两条

**① 闸门必须有豁免条款。** 闸门设计成「一律触发」会被绕过或降低使用意愿；正确形态是「触发条件 + 豁免条件 + 禁令 + 逃生舱」。例：spec-first 触发 = 3+ 文件/跨模块/涉枚举状态机/需求含糊；豁免 = 1~2 文件且无分支；逃生舱 = `--no-verify`（知情选择，非默认路径）。

**② 机器校验只覆盖可机械判定的子集。** 判据：
- 文件数 / 路径正则 / 提交信息格式 → **hook**
- AST 可判定的代码模式（绕过封装、内联样板） → **lint 插件**
- 「涉枚举状态机」「需求含糊」「是否漏改引用点」 → **留在规则里**，靠流程 + 影响面清单兜底

不要试图用脚本判语义，也不要指望纯提示能拦住可机械判定的问题。

## 四、体系的自我维护

体系不是一次搭完就不动的，靠三个机制自生长：

1. **决策沉淀**（每次达成长期结论）→ `decisions.md` 追加一条 Dn；
2. **复盘三问**（每次事故/返工后）→ ① 避免此错需要什么规则？② 属于哪个文档？③ 放在文档的哪个位置？→ 立即写入，不停留在对话结论；
3. **定期瘦身**（入口与规则膨胀时）→ 长内容外链到 `doc/`，入口只留导航 + 红线。

## 五、已知失效模式

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| 入口文档没人读、与事实脱节 | 内容堆进入口 | 瘦身：只留导航，长内容外链 |
| 规则写了但 AI 不遵守 | 纯提示无机器校验 | 可机械判定的下沉为 hook/lint |
| 同一知识点两处维护后分叉 | 放错层（rules 与 doc 重复） | 用第二节决策树重新归位 |
| 规则被绕过 | 缺豁免条款，简单场景也被卡 | 补「豁免」与「逃生舱」 |
| 决策反复讨论 | 未沉淀或沉淀位置不对 | `memory.md` 强制追加 + 任务前先读 |
| skills 目录变成大杂烩 | 把项目事实塞进 skills | 用「复制到别的项目还成立吗」自查 |
