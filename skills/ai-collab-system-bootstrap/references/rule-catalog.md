# 规则目录与写法要点（`.agents/rules/`）

## 一、frontmatter 契约

```yaml
---
name: spec-first                    # 必填，与文件名一致（kebab-case）
description: 一句话说明「约束什么 + 什么时候生效」   # 必填，AI 判断是否读取的唯一线索
alwaysApply: true                   # 必填；true=常驻加载，false=按需加载
scene: git_message                  # 可选，场景化触发（如提交信息场景）
---
```

- `alwaysApply: true` → **闸门与硬约束**（不遵守会出事）：spec-first / verification / workflow-guide / memory / project_rules / api-convention / i18n / git-commit-message。
- `alwaysApply: false` → **大体量项目事实**（读了才有用，常驻浪费上下文）：design-system 这类对照表型规则。**按需加载靠 `description` 触发**，所以 description 必须写清「何时必须读」。
- `scene` → 只在特定动作时注入，如 `scene: git_message` 让提交场景自动带上规范。

## 二、规则分类学

| 类型 | 特征 | 代表 | alwaysApply |
| --- | --- | --- | --- |
| **闸门型** | 定义「什么时候必须停下来等确认 / 什么不许做」 | spec-first、verification | true |
| **路由型** | 把意图映射到流程，保证场景一致性 | workflow-guide | true |
| **沉淀型** | 约束 AI 主动写回文档，让体系自生长 | memory | true |
| **引用型** | 指向代码规范总纲，声明强制引用关系 | project_rules | true |
| **约定型** | 统一某类代码/文案的写法 | api-convention、i18n、git-commit-message | true |
| **事实型** | 项目专属的对照表/清单（token、权限码、命名护栏） | design-system | **false** |

## 三、逐条要点

### spec-first（闸门 · 最重要）

**结构必须四段齐全**：触发条件 / 闸门流程 / 禁令 / 豁免。

- 触发：预计 3+ 文件、跨模块、涉业务分支或枚举状态机、需求含糊或存在多种解读（满足任一）。
- 流程：判断复杂度 → 生成 `change-id`（`YYYYMMDD-<kebab主题>`）→ 产出三层文档到 `doc/changes/<change-id>/` → **停下等确认** → 确认后按 tasks 逐项实现。
- 禁令：未确认禁止创建/修改/删除 `{{SRC_DIR}}`；禁止以「先做个最小实现」绕过；等待确认期间禁止顺手动其它文件。
- 豁免：1~2 文件且无业务分支；纯文档/配置/构建调整；用户明确说「不用出方案，直接改」。

**三层文档必须含「影响面清单」**——历史事故（语言下拉改造漏改 2 个页面）证明：没有影响面清单，跨模块改动必漏。

### workflow-guide（路由）

一张表把「用户意图 → 工作流 → 关键闸门」写死，并给出判定规则：无法确定意图先用澄清技能；混合意图按最重的执行并显式拆分；简单改动豁免闸门但**不豁免**质量验证；冲突时以 spec-first 禁令为准。末尾列「所有工作流的公共红线」。

### verification（完工自检）

五类自检项：类型检查 / lint / 目标验证（把任务转成可验证目标并真跑通）/ 范围收敛（每处改动可追溯到诉求）/ 清理孤儿（只删本次改动产生的无用引用）。

**单元测试必须带豁免条款**：mock 成本高（依赖浏览器 API/网络/DOM）或效果不明显（纯排版/样式/透传）可不写，但必须在交付说明中列出「哪些文件没写、豁免原因、需人工测什么」。

**留痕要求**：交付说明必须附命令输出摘要（如「type-check: 无错误」）作为「实际执行过」的证据。

### memory（决策沉淀）

- 承接任务前**先读** `decisions.md`，避免推翻既有结论或重复讨论；
- 达成长期决策后**主动追加**（无需用户提醒）；只追加不覆盖，编号取最大值 +1，格式：`## Dn · 标题` + 结论 + 理由 + 日期；
- 明确「不需要记录的情况」避免噪音：一次性实现细节、临时调试结论、已存在且未变化的决策；
- 写入后**告知用户**新增了哪条（编号 + 标题）；
- 附「复盘三问」机制（事故 → 文档循环）。

### project_rules（引用总纲）

极短，只声明强制引用关系：生成的代码必须遵循 `X` 规范 skill、涉及 `Y` 技术时必须额外读 `Z` 规则；并声明「入口文档中提到的技能必须在 skills 目录真实存在」这条一致性约束。

### api-convention / i18n / design-system（约定与事实型示例）

这三条是**技术栈相关的示范**，移植时按新项目栈改写或删除：

- `api-convention`：统一请求客户端、端点集中在 `baseApi`、公共响应类型复用、拦截器行为（成功解包 / blob 不解包 / 401 全局处理）、请求头自动注入清单。**要点是把「调用方必须知道的隐式行为」显式写出来**。
- `i18n`：目录镜像、键名约定、注册规则、新增检查清单，以及**「缺键不报错会静默回退」这类陷阱必须写明**。
- `design-system`：`alwaysApply: false`；开头写「何时使用」；列必读文档表；给自查清单；给「新 token 命名护栏 + 落地三步」。**陷阱类内容单独成节**（禁用类名清单、既定事实不改名清单）。

## 四、规则写作红线

1. **必须有豁免/边界**，否则规则会被绕过或让人不敢用；
2. **不重复**：同一件事只在一条规则里写，其它地方用链接引用；
3. **写明陷阱**：项目里「不报错但会错」的地方（静默回退、缺省值、隐式解包）最值得写进规则；
4. **可验证**：规则里的每条要求最好能被命令、清单或钩子验证；纯口号不写；
5. **长度控制**：单条规则超过 ~150 行就该拆分或外链到 `doc/`；
6. **改动规则要同步入口**：`AGENTS.md` 的规则表必须同步增删。
