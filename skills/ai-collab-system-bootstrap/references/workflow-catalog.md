# 工作流目录与写法要点（`.agents/workflows/`）

## 一、为什么需要工作流层

规则（rules）解决「不许做什么」，工作流解决「按什么顺序做」。工作流把同类任务的标准步骤固化下来，避免每次即兴发挥导致质量波动。

**路由靠决策表，不靠 AI 自觉**：`workflow-guide.md` 把意图映射到工作流，是唯一入口。

## 二、路由原则（表不在此重复）

> **单一事实来源**：意图→工作流的映射表只在 `assets/rules/workflow-guide.md` 维护；本节只记录「搭建或改造工作流」时需遵守的原则，不复制表内容。

1. **一致性由决策表保证**，而非 AI 自觉——决策表必须显式给出「请求类型 → 工作流 → 关键闸门」三列；
2. **表里只放索引**：步骤细节写在各工作流文件内。路由表若同时抄了一份步骤，任何改动都要改 N 个文件（这正是体系要避免的维护成本）；
3. **判定规则要覆盖四种情形**：意图不明（先澄清再路由）、混合意图（按最重执行 + 显式拆分）、简单改动（豁免闸门但不豁免质量验证）、规则冲突（以 spec-first 禁令为准）；
4. **新增/删除工作流必须同步三处**：`assets/rules/workflow-guide.md` 决策表、`assets/AGENTS.template.md` 流程索引、本文件第三节。

## 三、四条工作流的步骤骨架

### feature-development（新功能）

```text
需求澄清 → 复杂度判断（spec-first 闸门）→ 读项目事实（决策记忆 + 业务域文档 + 接口文档）
→ 模板化实现（列表页/API/状态管理/下拉 hook/i18n 骨架）
→ i18n 补词条（中英镜像）
→ 质量验证（类型检查 + lint 保持绿；交互用浏览器工具冒烟）
→ 范围核对（对照影响面清单剔除无关变更）
→ code-review（对 diff；安全场景用安全审查）
→ 完工自检（verification）→ 复盘沉淀（memory 三问）
```

闸门：步骤 2 未确认禁止改源码；步骤「质量验证」未通过不得提交。

**要点**：步骤 4 必须指向可复制的代码骨架模板（`doc/templates/code/`）——这是「同一类模块长得一样」的保证。

### bug-fix（缺陷修复）

```text
复现（能写复现用例的先写，TDD 优先）→ 定位根因（源码 + 业务域文档「已知坑」+ git log；区分数据/展示/逻辑问题）
→ 复杂度判断（spec-first）→ 最小修复（只改根因）→ 回归验证（修复点 + 关联展示位，涉及枚举/下拉检查全部引用点）
→ 质量验证 + 范围核对 + code-review → 复盘沉淀（新坑补进业务域文档「已知坑」）
```

闸门：**未复现不得动手改码**（防盲改）；变更行必须全部可追溯到根因。

### hotfix（线上紧急）

```text
确认紧急程度（是否真阻断）→ 最小修复（禁止夹带重构/新功能）
→ 立即验证（关键路径冒烟）→ 提交并部署（fix 前缀 + 标注 hotfix）
→ 24h 内补录变更文档（含事故背景、根因、止血 vs 根治）→ 复盘沉淀
```

闸门：止血改动必须最小；**事后补录不可跳过**（豁免的是「先行」，不是「补录」）。

### refactor（重构 / 结构调整）

```text
范围界定（行为不变/性能/可维护性）→ 三层文档（必走，影响面清单覆盖所有引用点，停下等确认）
→ 行为不变原则（不混入功能改动；必要时先写行为基线用例）
→ 分步迁移（每步独立可验证，路径迁移用 git mv 保历史）
→ 引用与索引同步（入口文档/架构指南/业务文档/交叉引用）
→ 质量验证 + diff 范围核对 + code-review + 受影响页面冒烟 → 决策沉淀 + 变更归档
```

闸门：三层文档未确认禁止动码；diff 中不得出现与重构无关的功能改动。

**要点**：步骤「引用与索引同步」是重构最容易漏的一步——路径变了，`AGENTS.md`、`doc/architecture/`、rules 里的交叉引用都会失效。

## 四、所有工作流的公共红线

写在 `workflow-guide.md` 末尾，避免每条工作流重复：

- 复杂需求未确认前禁止改源码（spec-first）；
- 动手前先读：`.agents/memory/decisions.md` + `doc/business/` 对应域文档 + `doc/api` 对应版本；
- 完成前必跑：`{{TYPE_CHECK_CMD}} && {{LINT_CMD}}` + verification 自检；
- 接口变更：先在 `doc/api` 更新事实，再在 `doc/changes` 记录影响面；
- 提交信息遵循项目提交规范。

## 五、新增工作流的做法

1. 先问：它能被现有 4 条之一覆盖吗？能覆盖就不要新增（工作流数量与维护成本正相关）；
2. 新增后**必须同步两处**：`workflow-guide.md` 决策表 + `AGENTS.md` 的流程索引表；
3. 每条工作流统一格式：`> 适用：… 由 workflow-guide 决策表路由` → `## 步骤`（编号列表）→ `## 关键闸门`（未满足会出什么事）；
4. 步骤里的命令、模板路径、文档路径必须是**目标项目真实存在的**，否则工作流形同虚设。
