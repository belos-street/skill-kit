# 完工前自检规则

在声明任务「完成」之前，必须完成以下自检，确保交付物可验证、可运行。**不要仅凭「代码看起来对」就宣布完成。**

## 一、通用自检项（每次必做）

1. **类型检查**：涉及类型化语言改动时，运行 `{{TYPE_CHECK_CMD}}`（或确认 IDE 诊断无错误）。
2. **Lint**：改动文件通过 Lint，必要时运行 `{{LINT_CMD}}`。
3. **目标验证**：把任务转化为可验证目标并实际跑通，例如：
   - 修 Bug → 先有能复现的用例，再修复并确认其通过；
   - 加功能 → 实际运行 / 调用，确认行为符合预期；
   - 重构 → 确认改动前后行为一致、相关测试通过。
4. **范围收敛**：每一处改动都能追溯到用户的明确诉求，不夹带无关「顺手优化」。
5. **清理孤儿**：仅删除因本次改动而产生的无用 import / 变量 / 函数，不动既有死代码。

## 二、测试要求（含豁免条款）

- **默认要求**：对新增或修改的**纯逻辑、工具函数、可独立验证的模块**，应补充或更新单元测试并运行通过（`{{TEST_CMD}} <path>`）。
- **豁免条款**：满足以下任一情况时**可以不写测试**，但必须满足「豁免说明」要求：
  1. **模拟成本偏高**：强依赖浏览器 API、网络请求、DOM 交互、第三方运行时等，mock 代价远超测试收益；
  2. **测试效果不明显**：如纯 UI 排版、样式、文案、简单透传逻辑，单测难以覆盖其真实价值。
- **豁免说明（必须）**：对于豁免测试的改动，需在交付说明中**明确指出**：
  - 哪些文件 / 模块未写测试；
  - 豁免原因（对应上述哪一条）；
  - 需要**人工手动测试**的具体步骤或关注点。

## 三、交付前确认

- 相关命令实际执行过，而非仅「预期会通过」。
- 若存在无法自动验证、需用户手动操作的部分，已清晰列出清单与步骤。

## 四、验证留痕

- 交付说明（回复 / PR 描述）必须附 `{{TYPE_CHECK_CMD}}` / `{{LINT_CMD}}` 的**输出摘要**（如「type-check: 无错误」「lint: 0 errors, 3 warnings」），作为「实际执行过」的证据，供人工抽查；
- 无法附输出（如命令被中断）时，须明确说明最后执行时间与结果状态；
- 测试豁免不豁免本项：豁免的是单测，类型检查与 lint 摘要照常附。
