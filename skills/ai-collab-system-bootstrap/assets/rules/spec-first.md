# 规范先行闸门规则

复杂需求必须「先出方案 → 等确认 → 再动码」。**未经用户确认，禁止创建/修改任何 `{{SRC_DIR}}` 业务代码。** 本规则是强制闸门，不是建议。

## 一、何时触发（满足任一即触发）

1. 预计改动 **3+ 个文件**；
2. **跨模块 / 跨目录**改动（如同时涉及 API 层、多个页面、hooks）；
3. 涉及**业务分支、枚举、状态机**变更（如新增状态、调整枚举顺序）；
4. 需求**含糊或存在多种实现解读**，需要先对齐方案。

## 二、闸门流程（触发后必须执行）

1. **判断复杂度** → 命中上述触发条件才继续；简单改动直接干活（见「豁免」）。
2. **生成 change-id** → `kebab-case`：`YYYYMMDD-<主题>`，如 `20260807-task-list-column`。
3. **产出三层文档**（模板见 `doc/templates/change/`，结构见下）→ 写入 `doc/changes/<change-id>/`。
4. **产出后立即停止**，向用户呈现方案，等待用户明确「确认通过」；优先走平台的 **Plan 模式 / 方案确认机制**。
5. **确认后执行** → 按 `tasks.md` 逐项实现，每项过验收点，最后走 `verification` 规则自检。

### 三层文档结构

#### proposal.md（为什么做）

- 背景与问题
- 目标与非目标
- 方案选型（如有多个方案，列出权衡与推荐）
- **影响面清单**（涉及页面 / 组件 / API / 枚举 / hook，必须覆盖所有引用点——缺影响面清单是跨模块改动漏改的头号原因）
- 验收标准

#### design.md（怎么做）

- 技术设计（数据结构、状态流、接口签名）
- 涉及文件清单（精确到路径，分「改动 / 新增 / 删除」三类）
- 与 `doc/api` 的对应关系（接口变更先更新事实层）
- 风险与已知坑（引用 `.agents/memory/decisions.md`）

#### tasks.md（拆着做）

- 任务列表，每项：目标 → 涉及文件 → 验收点
- 按依赖排序，标注可独立验证项

## 三、禁令

- 未经确认，禁止创建/修改/删除任何 `{{SRC_DIR}}` 业务代码；
- 禁止以「我先做个最小实现 / 先改这一处」等理由绕过闸门；
- 禁止在等待确认期间顺手动其它文件。

## 四、豁免（不触发闸门）

- 简单改动：预计 **1~2 个文件**、无业务分支、需求明确无歧义；
- 纯文档 / 配置 / 构建脚本调整（不涉及业务逻辑）；
- 用户明确表示「不用出方案，直接改」。

## 五、与其它规则衔接

- 用户确认后的实现，仍需遵循 `verification.md` 完成完工前自检；
- 接口变更时：先在 `doc/api` 更新事实，再在 `doc/changes` 记录本次影响面；
- 涉及既有约定前，先读 `.agents/memory/decisions.md`。
