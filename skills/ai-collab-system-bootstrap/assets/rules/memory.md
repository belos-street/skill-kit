# 决策记录沉淀规则

让 `.agents/memory/decisions.md` 由 LLM 在对话中**自动维护**，而非仅靠人工。

## 一、承接任务前：先读

涉及既有约定的任务（目录归属、工具链选型、命名/架构约定、流程规范等）开始前，先阅读 `.agents/memory/decisions.md`，**避免推翻既有结论或重复讨论**。

## 二、达成决策时：主动追加

当对话中**敲定**了具有长期约束力的技术或流程决策时（如：选用/弃用某工具或库、目录/文件归属、命名或架构约定、是否迁移、流程规范变更等），须在该决策确定后，**主动追加**到 `decisions.md`，无需等用户提醒。

### 不需要记录的情况（避免噪音）

- 一次性实现细节、临时调试结论；
- 已存在且未变化的决策；
- 无长期复用价值的单次指令。

## 三、记录格式（严格遵守）

1. **只追加、不覆盖**：在文件末尾新增，编号取当前最大值 +1（如 D7、D8…）。
2. 沿用既有格式：

```markdown
## Dn · 决策标题

- **结论**：……
- **理由**：……
- **日期**：YYYY-MM
```

3. **告知用户**：写入后在回复中简要说明新增了哪条决策（编号 + 标题），便于用户核对或纠正。

## 四、复盘沉淀：事故 → 文档循环

每次开发/修复完成后的复盘，除了「是否新增决策」，还要按**三个问题**把教训落回文档，让体系自生长：

1. **避免此错需要什么规则？** → 若无对应规则，考虑新增或补强（spec-first / verification / api-convention 等）；
2. **属于哪个文档/规则？** → `doc/business/<域>.md` 的「已知坑」/「关键检查清单」、`doc/architecture/` 指南、或新决策 D-n；
3. **放在文档的哪个位置？** → 工作流程 / 不适用场景 / 关键检查清单 / 已知坑，明确落点后**立即写入**，不要只停留在对话结论。

> 落地素材示例：某域文档的「已知坑」记录「筛选配置加载时序」；某决策记录「下拉数据源统一由后端接口驱动」。后续事故按此循环持续补充。
